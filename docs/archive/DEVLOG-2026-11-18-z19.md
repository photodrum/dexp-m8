# 2026-11-18 — замечание 19: падение в нативе на кегле 8–12 (SIGBUS в кеше глифов)

Замечание 19 `docs/ROADMAP.md`. Найдено 2026-11-17 при проверке удержания после смены кегля.
Натив и движок — работа на Opus.

## Симптом

`Fatal signal 7 (SIGBUS), code 1 (BUS_ADRALN)` в потоке `dexp-engine`, стек:

```
#00 LVFontGlyphCacheItem::newItem(...)  include/lvfntman.h:169
#01 newItem(...)                        src/lvfntman.cpp:1099
#02 LVFreeTypeFace::getGlyph            src/lvfntman.cpp:3722
#03 LVFreeTypeFace::DrawTextString      src/lvfntman.cpp:5039
```

Кегли 8…12 падают, 13 и выше — нет. Нестабильно: на кегле 11 — 3 падения из 5 запусков.

## Что пробовал и что дало

1. **ASan на хосте** (`g++ -fsanitize=address`, тот же `cre.cmake`, `LVDocView` + FB2 + наши
   шрифты из `res/font`, все страницы «Воскресения» дважды, кегли 8…12, два прохода) —
   **чисто**. И это не «повезло»: ASan подменяет аллокатор и отдаёт блоки с бо́льшим
   выравниванием, поэтому исходный дефект под ним не воспроизводится в принципе.
2. **ASan на книге** (отдельный бинарник под armeabi-v7a, `posix_memalign`-подобный аллокатор
   ASan, тот же путь `LVDocView` → `setFontSize` → `Draw`) — тоже **чисто**. Тот же эффект.
3. **Настоящее приложение на книге** — падение воспроизведено с первого запуска при
   `text_size 11` (правка `shared_prefs/shell.xml` через `run-as`, затем `am start --es read`).
4. **Дизассемблер настоящей `.so`** (`llvm-objdump -d` из NDK, дебажная сборка не стрипнута) —
   причина видна сразу:

   ```
   17fc9a: blx     malloc
   ...
   17fcac: vst1.64 {d16, d17}, [r1:128]!   ← NEON-запись 16 байт, требует адрес ×16
   ```

## Причина

`LVFontGlyphCacheItem` объявляет хвостовой буфер как `alignas(16) lUInt8 bmp[1]`
(`lvfntman.h:146`, комментарий «we just use 16 everywhere» из koreader/crengine#441).
Из-за этого `alignof(LVFontGlyphCacheItem) == 16`, и clang на armv7 обнуляет
`prev_global`/`next_global` одной 16-байтной NEON-записью по **адресу объекта**.

Память под объект берётся `malloc` (`newItem`, две перегрузки), а bionic на armv7 даёт
выравнивание только 8. Когда `malloc` возвращает блок по адресу ≡ 8 (mod 16) — SIGBUS
`BUS_ADRALN` прямо в `newItem`. Адрес падения `0xf1d1ddb8 % 16 == 8`.

Отсюда и «нестабильность 3 из 5»: зависит от того, какой адрес вернул конкретный `malloc`,
а кегль меняет картину аллокаций. К R5 отношения не имело, как и предполагалось.

## Правка

`tools/patches/crengine-19-glyph-align.patch` (55 строк, один файл `crengine/include/lvfntman.h`):

- новый `static void * allocItem(size_t)` — `posix_memalign` с `alignof(LVFontGlyphCacheItem)`
  (то есть 16); на `_WIN32`/`__SYMBIAN32__` остаётся `malloc`, там он и так даёт 16;
- обе перегрузки `newItem` (по символу и по глиф-индексу HarfBuzz) зовут `allocItem`.
  Третья точка, `LVFontBoldTransform::getGlyph` (`lvfntman.cpp:5721`), идёт через тот же
  `newItem` — правки не потребовала;
- `posix_memalign` освобождается обычным `free()`, поэтому `freeItem` не менялся;
- `getSize()` по-прежнему считает `offsetof(...,bmp) + pitch*h` — размер не изменился.

Патч применяется при конфигурации CMake (`engines/cre.cmake`, `git apply` идемпотентен):
правка не потеряется при `git submodule update`. Проверено обе ветки: патч уже наложен —
молча пропускается; откатили `lvfntman.h` — накладывается заново.

## Грабли

- **ASan здесь не помощник** (в отличие от записи в ROADMAP, где он предлагался): подменённый
  аллокатор выравнивает блоки, и именно поэтому дефект под ASan не виден. Причину дал
  дизассемблер настоящей `.so` — `vst1.64 [r1:128]` в `newItem`.
- **Стенд на системных шрифтах ничего не показывает:** без Literata начертание подменяется,
  и картина аллокаций другая. Воспроизводить надо с нашими `res/font` (или на приложении).
- `adb shell run-as … sed -i` по `shared_prefs/shell.xml` не работает (кавычки и NUL в
  аргументах): `pull` через `run-as cat` → правка локально → `push` в `/data/local/tmp` →
  `run-as cp` обратно.
- Отдельный ASan-бинарник под устройство требует рядом `libclang_rt.asan-arm-android.so`
  **и** `libc++_shared.so` из NDK (`ANDROID_STL=c++_shared`), иначе
  `CANNOT LINK EXECUTABLE: library "libc++_shared.so" not found`.
