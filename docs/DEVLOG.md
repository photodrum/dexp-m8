## 2026-11-10 — п. 3, шаг 7: B2 и B11 на данных из базы (`LibraryScreen.kt`, `LibraryDb.kt`)

`LibraryScreen` держит `LibraryDb` и `Scanner`; заглушки книг убраны. Один источник данных на оба
вида: `refresh()` читает страницу (6 строк) в `rowIds` / `books` (B2) / `gridBooks` (B11), число
книг `total`, `selectedId` = `lastOpened()`; подзаголовок «N книг · X ГБ» считается по базе.
- Выбранная (вдавленная) строка/карточка — `rowIds[i] == selectedId`; нет открытых — нет выбранной.
- Статусы базы переводятся явно: `STATUS_READING` → `ST_PROGRESS`, `STATUS_READ` → `ST_READ`,
  иначе `ST_NEW` (числа не совпадают, см. шаг 4). Автор без данных — «Автор неизвестен»; в B2 к
  автору добавляется формат («Лев Толстой · FB2»), в B11 — нет (как в макете).
- Сортировка: «По автору» / «По дате» → `SORT_AUTHOR` / `SORT_RECENT`, «Новые» → `SORT_ADDED`,
  «Непрочитанные» — фильтр `status = новая` (порядок по названию). Листание, смена сортировки и
  вида читают базу заново, `page` обрезается по числу страниц. Вид (список/сетка) страницу не
  сбрасывает: данные те же, 6 на страницу в обоих.
- `LibraryDb`: `count(onlyNew)`, `list(..., onlyNew)`, новый `totalSize()` — для подзаголовка и
  фильтра «Непрочитанные».
- Право и скан: `onAttachedToWindow` — `addStorageListener`, `refresh()`, при праве
  `Scanner.start { post { refresh/layout/redraw } }` (только если экран ещё привязан), без права
  — `act.requestStorage`. `onDetachedFromWindow` — отписка. Слушатель при `ok` запускает скан.
- Пустое состояние (снимка B46 нет): вдавленная панель + строка «Нет доступа к памяти» /
  «Книг пока нет» с подсказкой; зона касания — вся панель. Нет права: первое нажатие — системный
  диалог, дальше — `ACTION_APPLICATION_DETAILS_SETTINGS`.
- Нажатие на книгу: `db.markOpened(id)` и переход в читалку (заглушка); при возврате
  `onAttachedToWindow` обновит выбранную строку (экран кэшируется в `EinkActivity.screens`).

## 2026-11-10 — п. 3, шаг 6: разрешение на чтение памяти (`EinkActivity`, манифест)

Манифест: добавлен `READ_EXTERNAL_STORAGE` (был только `WRITE_…` для `DexpM8-crash.txt`).
`EinkActivity` (Opus, архитектура):
- `hasStorage()` — есть ли `READ_EXTERNAL_STORAGE`;
- `requestStorage(done)` — `Activity.requestPermissions` для READ + WRITE (одна группа STORAGE,
  один диалог); `done(ok)` в UI-потоке, при уже выданном праве — сразу. Пока диалог открыт,
  повторный вызов только ставит `done` в очередь: второй `requestPermissions` поверх открытого
  система отменяет;
- `addStorageListener` / `removeStorageListener` — смена права (диалог или «Настройки», пока
  оболочка в фоне — проверка в `onResume`, если диалог не открыт);
- запрос на холодном старте (`savedInstanceState == null`) после показа B1, а не до: под
  системным диалогом уже нарисован экран, нет белого кадра. Если показ B1 упал — запроса нет.
- `onRequestPermissionsResult` верит `checkSelfPermission`, а не `grantResults` (пуст, если
  диалог прервали). В трассе — строки `storage: granted|missing|request|denied`.

Контракт для 3.7 (Sonnet): `LibraryScreen` при показе зовёт `act.requestStorage { ok -> … }`,
при `ok` — `Scanner.start { r -> post { … } }` (onDone идёт в фоновом потоке); подписка
`addStorageListener` в `onAttachedToWindow`, отписка в `onDetachedFromWindow` — так экран
пересканирует, если право выдали в «Настройках». Без права — пустое состояние B46 «нет разрешения»
(в снимке пока нет; до снимка — строка-заглушка). Список слушателей и очередь чистятся в `onDestroy`.

Грабли: отзыв права в «Настройках» Android убивает процесс — отдельной обработки не нужно, при
следующем запуске `storageOk` считается заново. После «Больше не спрашивать» `requestPermissions`
сразу возвращает отказ без диалога — повторно на холодном старте не мучает пользователя, но и
диалога нет; для этого случая B46 должен вести в «Настройки» приложения (`ACTION_APPLICATION_DETAILS_SETTINGS`)
— это 3.7 или первый запуск B8. `typecheck.sh` из Cline без `JAVA_HOME`/`PATH` из `BUILD.md`
падает «java: command not found» и пишет «классов собрано: 0» — выглядит как успех, смотреть число.

Проверки: `typecheck.sh` — 0 `error:`, 42 класса (лямбды — не отдельные классы). Gradle
`assembleDebug` — `BUILD SUCCESSFUL`; `aapt2 dump permissions` — `READ_EXTERNAL_STORAGE` и
`WRITE_…` в APK, `targetSdkVersion 27`. **На книге не проверено** — сверка в 3.8: диалог на
первом запуске, строки `storage:` в `DexpM8-trace.txt`, отказ → повторный запуск.

## 2026-11-10 — п. 3, шаг 5: сканер книг (`core/Scanner.kt`)

`Scanner(ctx, db: LibraryDb)`: `start(onDone)` — фоновый поток `library-scan` (приоритет MIN, daemon,
один проход за раз, `false` — предыдущий ещё идёт; `onDone` вызывается на этом же потоке, экран
переносит результат в UI сам); `scan()` — то же синхронно, не из UI. Результат — `Scanner.Result`
(`skipped`, `seen`, `added`, `updated`, `removed`, `failed`, `ms`).

**Как идёт проход:**
1. Нет `READ_EXTERNAL_STORAGE` или хранилище не `MEDIA_MOUNTED` → `Result.skipped` с причиной, база
   не трогается (пустой обход не должен стирать библиотеку).
2. Кандидаты: рекурсивный обход `<хранилище>/Books` (глубина до 12, скрытые `.х` пропускаются) +
   `MediaStore.Files` (`_data LIKE '%.ext'`) для книг вне `Books`. Из MediaStore не берутся `txt`,
   `rtf`, `doc` (слишком много посторонних файлов), скрытые пути и `Android/`.
3. Форматы: `fb2`, `fb2.zip`, `epub`, `mobi`, `txt`, `rtf`, `doc`, `pdf`, `cbz`, `djvu`, `djv`
   (по `READER_SPEC`).
4. `db.stamps()`; файл с тем же размером и mtime пропускается. Остальное — в одном
   `db.inTransaction`: `upsert`, затем `remove` для путей, которых нет среди найденных **и** нет на
   диске (книга, пропавшая только из MediaStore, но лежащая на диске, не удаляется).
5. Метаданные: только `fb2` — `NativeBook.metaFb2(file, buf)`, один `ByteArray(META_HEAD)` на проход.
   `title` — из `Meta`, иначе имя файла без расширения; `authorSort` — «Фамилия Имя» первого автора,
   без них ник, иначе `null`; пустые строки → `null`. У остальных форматов и `fb2.zip` — только
   название из имени файла (метаданные движков — этап читалки).

Решения: ошибка разбора одного файла (`Exception`) считается в `failed` и не прерывает проход;
ошибки базы не гасятся — исключение откатывает транзакцию. Файлы нулевого размера пропускаются.
Лог — `Log.i`/`Log.w` с тегом `DexpM8`, итоговая строка со счётчиками и временем.

Проверки: `typecheck.sh` — 0 `error:`, 42 класса (было 37; +5 от `Scanner`). **На устройстве не
запускалось** — вызывающего кода нет (подключит шаг 3.7), а разрешение на чтение выдаёт шаг 3.6;
без него `scan()` вернёт `skipped`. Хостового теста нет: класс целиком завязан на `Context`,
`Environment` и `MediaStore`.

Не проверено, смотреть на книге (3.8): что `getExternalStorageDirectory()` на ней действительно
`/storage/emulated/0`, а пути из `MediaStore` начинаются с него же (иначе фильтр `startsWith(base)`
отбросит всё из MediaStore); время прохода на реальном наборе `Books`.

## 2026-11-10 — п. 3, шаг 4: база библиотеки (`core/LibraryDb.kt`)

`LibraryDb(ctx) : SQLiteOpenHelper` — файл `library.db`, версия 1, WAL (`enableWriteAheadLogging`
в `onConfigure`: чтение экрана не ждёт запись сканера). Одна таблица `books`: `_id`, `path`
(UNIQUE), `size`, `mtime`, `format`, `title`, `title_sort`, `author`, `author_sort`, `series`,
`series_num`, `lang`, `cover_id`, `progress` (0..100), `status`, `added`, `opened`. Индексы:
`title_sort`; `author_sort, title_sort`; `opened`.

**Контракт для сканера (3.5):**
- `stamps(): HashMap<String, Stamp>` — путь → размер и mtime; файл с тем же stamp не разбирать.
- `upsert(Info)` — нового вставляет (`status` «новая», `added` = сейчас), известному обновляет только
  метаданные и stamp; `progress`, `status`, `opened`, `added` не трогает. `Info.authorSort` строит
  сканер: «Фамилия Имя» первого автора (из `Meta.lastName`/`firstName`, иначе `nickname`), `null` — нет.
  `Info.title` не пустой: при `metaFb2 == null` сканер берёт имя файла без расширения.
- `remove(paths)` — для пропавших файлов; `inTransaction { … }` — весь проход одной транзакцией
  (вложенные `upsert`/`remove` присоединяются к ней; без неё fsync на каждую книгу).
- Статус: `STATUS_NEW` 0 / `STATUS_READING` 1 / `STATUS_READ` 2. **Не совпадает** с `ST_*` в
  `LibraryScreen` (`ST_PROGRESS` 0, `ST_NEW` 1, `ST_READ` 2): «читается» и «новая» там
  поменяны местами. Экраны в шаге 3.7 переводят значения явно, а не приводят числа друг к другу.

**Для экранов (3.7):** `list(sort, offset, limit)` — страница, `SORT_TITLE/AUTHOR/RECENT/ADDED`;
`count()`, `find(path)`, `lastOpened()` (выбранная строка B2/B11; `null` — ничего не открывали),
`markOpened(id)`, `setProgress(id, pct)` (статус вычисляется: 100 — прочитана, >0 — читается, 0 — новая).

Решения: сортировка по `title_sort`/`author_sort` — ключ `LibraryDb.sortKey` (нижний регистр, «ё» как
«е»), потому что `ORDER BY` по кириллице в SQLite сравнивает байты, а `COLLATE NOCASE` — только ASCII.
`author_sort IS NULL` в `ORDER BY` — книги без автора в конце. `onDowngrade` пустой: `adb install -d`
ставит старый APK поверх нового, и без него `SQLiteOpenHelper` бросает исключение. `onUpgrade` пока
пустой — миграции появятся вместе с версией 2.

Проверки: `typecheck.sh` — 0 `error:`, 37 классов (было 30; +7 от `LibraryDb`). SQL проверен на хосте
`sqlite3` в Python (`build/check_db.py`, не в git): схема из исходника создаётся, 3 индекса, список
столбцов `COLUMNS` — 15, как в `entry()`, все четыре `ORDER BY` выполняются, UNIQUE по `path` держит.
**Сам класс на устройстве не запускался** — вызывающего кода нет (сканер — 3.5).

Грабли: `SQLiteDatabase.setWriteAheadLoggingEnabled` — с API 16 в `SQLiteOpenHelper`, а не в
`SQLiteDatabase`; в `onConfigure` нужен `db.enableWriteAheadLogging()` — поймал `typecheck`.


## 2026-11-10 — п. 3, шаг 3: метаданные FB2 в C-ядре (Opus)

Новая функция `book_meta_fb2()` в `book.c` — отдельный проход по `<title-info>`, тело не читается:
разбор останавливается на `</title-info>`, а при `<body>`/`<binary>` раньше него — выходит.
`book_parse_fb2()` не трогал, кроме общей `buf_normalize` (см. «Грабли»).

**Контракт для сканера (3.5):**
- Kotlin: `NativeBook.metaFb2(file, buf): Meta?`, буфер `ByteArray(NativeBook.META_HEAD)` (64 КБ)
  один на весь проход сканера — читается только начало файла. Есть и `metaFb2(data, len)`.
- `Meta`: `title`, `authors` (все `<author>` через «, »: «Имя Отчество Фамилия», без имени — ник),
  `firstName`/`middleName`/`lastName`/`nickname` — только первого автора (для сортировки и
  «Ф. Фамилия» на B2/B11), `series` + `seriesNum` (0 — нет номера), `lang`, `coverId` (id `<binary>`
  без `#`), `complete`. Любое поле может быть `null`.
- `complete = false` — `</title-info>` не попал в 64 КБ (огромная аннотация); поля, что успели, есть.
- `null` — не FB2 (нет `<title-info>`), неподдерживаемая кодировка или не поднялась `.so`.
  Сканеру в этом случае брать название из имени файла.
- `<author>` из `<document-info>` (автор файла) и `<src-title-info>` (оригинал перевода) не берутся.

Что умеет: кодировки UTF-8 (с BOM и без), windows-1251 (своя таблица 128 точек, сверена с
Python `cp1251`), latin-1; KOI8-R и UTF-16 — ошибка `ERR_ENCODING` (4, «unsupported encoding»).
Префиксы пространства имён (`fb:book-title`, `l:href`, `xlink:href`). Сущности, вложенные теги в
поле (`<emphasis>`) выбрасываются, пробелы схлопываются. Поле — не больше 4 КБ сырых байт и 1 КБ на
выходе, обрезка по границе символа UTF-8. Обрезанный посреди тега файл — не ошибка.

JNI: `metaFb2Native(data, len)` отдаёт `String[11]` (порядок — в комментарии `jni_bridge.c`), а
`Meta` собирается в Kotlin. Так из C не создаётся ни одного объекта своего класса — правило R8 не
нужно (проверено: `metaFb2Native` и `NativeBook$Meta` в release-dex есть). Строки — через
`NewString` (UTF-16), а не `NewStringUTF`: тот ждёт modified UTF-8 и с CheckJNI роняет процесс на
эмодзи и битых байтах из чужих FB2; битые байты -> U+FFFD.

Проверки: тест ядра на хосте (ASan + UBSan) — **34 ok, 0 FAIL** (было 9): образец, обрезка в любом
месте (все префиксы sample.fb2 в буфере ровно нужной длины), несколько авторов и ник, серия, сущности,
cp1251 + префиксы, BOM, `src-title-info`, KOI8-R/UTF-16/не FB2, длинное поле, 2000 прогонов мусора.
`gcc -Wall -Wextra -Wshadow -Wconversion` для `book.c` и `jni_bridge.c` (с `jni.h` из JDK) — 0
предупреждений. `typecheck.sh` — 0 ошибок, 30 классов (+ `NativeBook$Meta`). Gradle `assembleDebug
assembleRelease` — `BUILD SUCCESSFUL`; символ `Java_…_metaFb2Native` есть в `armeabi-v7a`, `arm64-v8a`;
`libdexp_core.so` в release: armeabi-v7a 13 144 Б, arm64 19 136 Б. На книге не проверялось —
вызывающего кода пока нет (сканер — шаг 3.5).

Грабли:
- `buf_normalize` терял пробел перед сущностью: «амперсандом &amp; кавычками» давало
  «амперсандом& кавычками» — и в теле книги тоже (старый тест этого не ловил). Исправлено, добавлена
  проверка `space before entity kept`. `&nbsp;` теперь схлопывается с соседними пробелами как обычный
  пробел. Это меняет текст блоков читалки — в лучшую сторону.
- Gradle, запущенный фоном из Cline через `( … ) &`, вставал в `T` (stopped) — клиент читал
  терминал. Работает так: `setsid nohup bash -c '… --console=plain' </dev/null >лог 2>&1 &`.
- «1 errors» в lint release — старое `targetSdk 27` (`abortOnError = false`), не от этого шага.
- Тест под ASan иногда падал `AddressSanitizer:DEADLYSIGNAL` до `main` — и на коде из `HEAD`
  тоже (8 из 60 против 8 из 60). С `setarch -R` (без ASLR) — 0 из 50 у обоих. Причина — ASan
  gcc 12 и ядро хоста 7.0. Команда теста в `BUILD.md` и `cpp/README.md` теперь с `setarch -R`.
