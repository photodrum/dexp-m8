Время уходит на декодирование фона/переднего плана IW44 и масштабирование 1240×1754 → 1404×1692 в `GREY8`. Страница чистого текста JB2 — типичный «книжный» DjVu. Цветных сканов с фоном на реальных книгах может быть много, поэтому вопрос для 7.4: допустимо ли ~1,5 с на цветную страницу (в читалке — предзагрузка следующей страницы и `DDJVU_RENDER_BLACK`/`MASKONLY` для текста). Не проверялось: реальные сканы, PSS при кэше больше 8 МБ.
- **Размер APK.** Чистая сборка (`rm -rf app/.cxx app/build`, `assembleDebug`): `app-debug.apk` — **4 951 689 байт** (после кода замеров в обеих пробах; до них было 4 950 721). В APK: `libdexp_core.so` 13 144, `libdexp_cre.so` 3 220 576, `libdexp_djvu.so` 548 808 байт.
- **Пустая рамка обложки EPUB — причина найдена и проверена на книге.** В «Немезиде» первая страница `titlepage.xhtml` — обложка Calibre: `<svg viewBox="0 0 200 307"><image xlink:href="cover.jpeg"/></svg>`. crengine рисует рамку SVG-блока, но картинку внутри не выводит (на снимке — чёрная рамка, внутри белое). Тот же файл с `titlepage.xhtml`, где вместо SVG стоит `<img src="cover.jpeg" style="width:100%">` (`/sdcard/Books/r0/nem-img.epub`, в остальном побайтно тот же), открывается: обложка видна целиком, градации серого в порядке, 2644 мс как и раньше. Вывод: проблема в SVG-обёртке, а не в JPEG и не в сборке crengine. Для читалки: брать обложку из OPF (`<meta name="cover">` → `cover.jpeg`) и рисовать самим; либо не показывать страницу обложки внутри книги. Правка самого crengine (SVG `<image>`) — только если понадобится.
- **Грабли замеров.** (1) `adb shell … --es probe` с кириллицей в пути работает, но цикл `while`/`grep -q` в скрипте с `logcat -d` под терминалом Cline подвисает — запускать по одному файлу в фоне и читать лог. (2) `screencap` сразу после запуска давал чёрный кадр (E-Ink не обновилась); через 10–15 с после старта снимок нормальный. (3) Управляющие последовательности терминала VS Code (`ESC]633…`) попали в `cre_probe.cpp` при записи файла через `sed`/`cat` из терминала — сборка падала на первой строке; убраны, проверка `grep -c $'\x1b'` = 0.
- **Что осталось для 7.4:** решение «идём / не идём» — по цифрам выше критерии (PSS ≤ 60 МБ, страница ≤ 300 мс) выполнены для crengine; для DjVu страница: цветной скан 1,47 с (не укладывается), чёрно-белый 0,16 с (укладывается).

## 2026-11-11 — решение по лицензии и PDF (Plan/Act, правки документов)

**Код и подмодули не тронуты** — только документы; код делается утром (7.3а–7.3б, Opus).

- **Проблема.** crengine — GPL-2.0 (`README.TXT`, «or any later version» только в 3 файлах из 115 → считаем only). MuPDF — AGPL-3.0. Вместе в одном APK нельзя (GPL-2.0-only несовместима с GPLv3/AGPLv3). DjVuLibre — GPL-2.0-or-later (`COPYING` — текст GPL v2) совместим. Остальное (fribidi LGPL-2.1+, libjpeg-turbo IJG+BSD-3, utf8proc MIT, xxhash BSD-2, libunibreak zlib, FreeType FTL/GPL-2.0, HarfBuzz MIT) совместимо.
- **Решение владельца.** PDF на книге не читает (медленно, неудобно) → MuPDF и PDF/CBZ убираем; проект — **GPL-2.0-only**. Системный `PdfRenderer` и PDFium не нужны. CBZ при желании позже — своим кодом (`java.util.zip` + `BitmapFactory`).
- **Скрытая зависимость:** `engines/cre.cmake` берёт freetype и harfbuzz из `third_party/mupdf/thirdparty/` (строки 10–11). Сначала 7.3а (отдельные подмодули), потом удалять MuPDF.
- **Документы:** README, READER_SPEC, ARCHITECTURE, DESIGN_USAGE, ROADMAP (шаги 7.3а–г), CONTEXT, BUILD. Не тронуты: прошлые записи DEVLOG и `docs/archive/` (история). Файла `LICENSE` ещё нет — шаг 7.3в.
- **Вопросы:** юридической экспертизы нет, оценка техническая. Запрос мейнтейнерам crengine по «or later» — по желанию. Чату дизайна: что на B31 остаётся без PDF, что показывать для `.pdf`/`.cbz` в библиотеке.
- **Прогноз (оценка, не замер):** до минимального релиза (оболочка + читалка до R3) ~5–7 недель, полный объём ROADMAP ~2,5–3,5 мес.
